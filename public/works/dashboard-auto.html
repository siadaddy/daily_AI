001_context.sql

자동화 이전: 매일 반복되는 작업의 시작

현장에서 담당자가 매일 아침 DMS 포탈에 로그인해 리포트를 받아서, 직접으로 취합 후 공유 엑셀로 가공해 배포하는 흐름에서 시작됐습니다. 지켜보기만 해도 이 과정이 자동화될 수 있다는 걸 담당자에게도 설명해 봤습니다.

자동화 이전

  • 매일 아침 로그인 + SMS/OTP 2단계 인증 수동 처리
  • 리포트 4종을 수동 다운로드로 수기 취합
  • 취합된 데이터로 엑셀 공유 파일에서 수동 관리
  • 특정 기간 데이터는 담당자에게 요청 필요
  • 지점 간 비교 담당자에게 수기 부탁

자동화 이후

  • 플레이라이트 OTP 자동 처리·인증까지 포함된 무인 로그인
  • 데이터가 DB로 자동으로 적재·정제·검증됩니다
  • 18개 이상 페이지에서 권한별로 실시간 조회
  • 특정 기간 데이터는 원하는 시간에 언제든 자동 조회
  • 텔레그램 봇으로 원격에서 상태확인·수동트리거·장애 알림 처리

003_engineering_log.sql

실제로 겪었고 직접 고친 문제들

프로덕션에서 실측으로 발견한 문제를 원인 분석까지 마치고 고친 기록입니다. 추측이 아니라 실제 데이터로 재현하고 검증한 것만 남겼습니다.

조용히 부풀어 오르는 매출

RESOLVED
문제

진행 중인 달을 매일 재추출하는 구조에서, 내용이 그대로인 행이 재적재 때마다 새 행으로 계속 쌓였습니다.

원인

중복 판정 기준(해시)에 "그날 리포트 안에서의 행 순번"이 섞여 있어, 순번만 바뀌어도 다른 행으로 인식됐습니다.

해결

해시 계산에서 순번을 제외하고, 과거 데이터 전체를 새 기준으로 재해시해 중복만 골라 정리하는 1회성 마이그레이션을 실행했습니다.

결과

진행 중인 달을 매일 재추출해도 안전한 단일 진실 소스 확보

취소되지 않았는데 사라진 인보이스

HARDENED
문제

인보이스가 "취소"가 아니라 "수정"되면 상쇄 없이 옛 버전이 원본에서 그냥 사라지는데, DB에는 옛 버전이 남아 집계를 부풀렸습니다.

원인

기존 로직은 "취소 쌍(+/-)"만 가정했고, 조용히 값만 바뀌는 수정 케이스는 처리하지 못했습니다.

해결

매 적재 후 최신 원본에 더는 없는 옛 행에 타임스탬프를 찍어 "살아있는 값"과 분리하고(이력은 보존), 원본과 DB를 양방향으로 대사하는 검사를 매일 자동 실행하도록 만들었습니다.

결과

집계 오차 제거 + 같은 문제의 재발을 스스로 감시하는 체계 확보

팀원의 HTML을 안전하게 공개하기

VERIFIED
문제

팀원이 만든 HTML을 로그인 없이 링크로 열람 가능하게 하되, 대시보드 로그인 세션은 절대 노출되면 안 됐습니다.

해결

Content-Security-Policy의 sandbox 격리로 이 문서를 매 요청 고유한 오리진으로 취급하게 만들어, 사용자 스크립트는 실행되지만 대시보드 쿠키·API는 접근할 수 없도록 설계했습니다.

검증

"안전할 것"이라는 설명에서 멈추지 않고, 브라우저 자동화로 쿠키 읽기·오리진 접근·API 호출이 실제로 전부 차단되는지 직접 재현해 확인했습니다.

결과

새 공유 기능이 기존 인증 경계를 절대 넘지 못한다는 것을 코드 리뷰가 아니라 실측으로 증명

쓰기 권한을 기능 단위로 쪼개기

SHIPPED
문제

서로 다른 기능(계정 관리, 게시판, 파일 공유)이 하나의 넓은 쓰기 권한을 공유하면, 한 기능의 버그가 전혀 무관한 데이터를 건드릴 위험이 있었습니다.

해결

기능마다 꼭 필요한 테이블 한두 개에만 쓰기 권한을 갖는 전용 DB 롤을 따로 만들고, 화면 조회는 항상 읽기 전용 롤만 쓰도록 코드 리뷰 규칙에 내장했습니다.

결과

새 기능을 추가할 때마다 최소 권한 원칙이 기본값으로 강제됨

React 서버 컴포넌트 경계에서 배운 것

RESOLVED
문제

클라이언트 컴포넌트에서 내보낸 공유 색상값을, 서버 컴포넌트 쪽에서 가져다 쓰자 렌더링에서 조용히 값이 사라져 그래프 색이 통째로 빠졌습니다.

원인

"use client" 파일의 export는 컴포넌트든 순수한 값이든 서버 코드 입장에선 전부 참조로 취급된다는 경계 규칙을 놓쳤습니다.

해결

공유 상수를 "use client"가 없는 중립 모듈로 분리해 양쪽 어디서나 안전하게 가져다 쓰도록 재구성했습니다.

결과

이후 비슷한 컴포넌트를 늘려도 같은 실수가 반복되지 않도록 원칙으로 문서화

같은 라인이 두 번 찍히면 사라지는 매출

RESOLVED
문제

한 인보이스 안에 완전히 같은 품목·같은 금액의 라인이 두 줄 있는 실거래가, 중복 방지 로직에 의해 한 줄로 붕괴돼 매출이 과소 계상됐습니다.

원인

내용이 100% 동일한 두 행을 "재추출로 생긴 중복"과 구분할 방법이 없었습니다.

해결

같은 파일 안에서 완전히 동일한 라인이 n번째 등장하면 해시에 등장 순번 표식을 붙여 서로 다른 행으로 인정하되, 하루 단위 재추출 시에는 여전히 같은 표식이 나오도록 설계해 중복 방지 효과는 그대로 유지했습니다.

결과

정상적인 반복 라인은 보존하고, 재추출로 인한 진짜 중복만 걸러내는 두 마리 토끼 확보

005_operations.sql

새벽에도, 말일 저녁에도 혼자 돌아간다

배포 이후가 진짜 시작이라는 생각으로, 사람이 지켜보지 않아도 스스로 감시하고 복구하는 운영 체계를 함께 만들었습니다.

01

이중화된 스케줄 트리거

시간 기반 트리거와 세션 기반 트리거를 함께 등록해, 서버 재시작이나 로그아웃 상황에서도 파이프라인이 조용히 멈추지 않도록 설계했습니다.

02

크로스 프로세스 잠금

스케줄러·운영 봇·대시보드 버튼이 동시에 같은 외부 세션을 건드리지 않도록 파일 기반 잠금으로 직렬화했습니다.

03

원격 운영 봇

텔레그램 봇으로 수동 트리거, 상태 확인, 장애 알림, 보고서 캡쳐까지 — 사무실 밖에서도 파이프라인을 확인·조작할 수 있습니다.

04

매일 자동 대사(對査)

원본 파일과 DB를 매일 자동으로 맞춰봐서, "원본에는 있는데 DB엔 없는" 조용한 누락을 스스로 찾아내도록 만들었습니다.

05

정기 백업 · 무결성 검증

재추출이 불가능한 과거 데이터를 지키기 위해 정기 백업과 검증 스크립트를 별도로 운영합니다.

007_closing.sql

혼자, 그러나 프로덕션 기준으로

이 프로젝트에서 가장 크게 배운 것은, 기능을 만드는 일보다 "이미 만든 기능이 계속 맞다는 것을 증명하는 일"이 더 오래 걸린다는 사실이었습니다. 대사 체크, 자동 코드 리뷰, 실측 검증을 습관으로 만들면서 — 혼자 개발해도 팀 단위 프로덕션이 요구하는 신뢰도를 유지할 수 있다는 것을 확인했습니다.

scl_agent — 딜러사 데이터 파이프라인 & 통합 대시보드
이 페이지는 실제로 설계·구축해 운영 중인 프로덕션 시스템을 바탕으로 작성했습니다. 다만 포트폴리오 공개 목적상 회사명은 익명화했고, 매출·재고 등 구체적인 영업 수치는 모두 배제했습니다. 화면 예시로 쓰인 수치는 실제 데이터가 아닌 레이아웃 설명용 예시입니다.
